# Plan Clarifications

## 1. Checkout Sessions for Separate Payments

**Important**: Each job has TWO separate payments (initial and balance), and each payment needs its own Checkout Session.

**Implementation**:
- **Initial Payment (Payment 1)**: Create Checkout Session on-demand when user clicks "Pay" for the first payment
  - Uses `initial_price_object.id` (e.g., `uid-amx-856-1`)
  - Includes discount coupon if applicable (only on first payment)
  - Session expires after 24 hours (Stripe default) or custom expiry
  
- **Balance Payment (Payment 2)**: Create Checkout Session on-demand when user clicks "Pay" for the second payment
  - Uses `balance_price_object.id` (e.g., `uid-amx-856-2`)
  - No discount (discounts only apply to first payment)
  - Session expires after 24 hours

**Why On-Demand**:
- Checkout Sessions expire (typically 24 hours)
- User might return days/weeks later to make second payment
- Creating sessions on-demand ensures they're always fresh and valid
- Sessions are cheap to create (Stripe's intended pattern)

**Storage**:
- Store checkout session **parameters** (not session IDs) in `state_management.object.checkout_session[]`:
  ```json
  "checkout_session": [
    {
      "initial": {
        "price_id": "uid-amx-856-1",
        "coupon_id": "uid-amx-856-coupon",
        "customer_id": "uid-amx-856-client"
      }
    },
    {
      "balance": {
        "price_id": "uid-amx-856-2",
        "customer_id": "uid-amx-856-client"
      }
    }
  ]
  ```
- When user clicks "Pay", API creates fresh session using these parameters
- Store actual session ID temporarily in sessionStorage (not in JSON)

## 2. User Tracking Events

**Purpose**: Track user behavior to inform state management and routing decisions.

**Events to Track** (in `state_management.client_status`):

1. **Contract Loaded**: When contract section becomes visible
   - Field: `contract_loaded` (timestamp: `"2026-01-03T14:30:00Z"` or `null`)

2. **Contract Scrolled**: When user scrolls to bottom of contract
   - Field: `contract_scrolled_complete` (boolean: `true` or `false`)
   - Use Intersection Observer API to detect when bottom element is visible

3. **Invoice Viewed**: When invoice section becomes visible
   - Field: `viewed_invoice` (already exists, timestamp or boolean)

4. **Contract Signed**: When user submits signature
   - Field: `signed_contract` (already exists, timestamp: `"2026-01-05T10:15:00Z"` or `null`)

5. **Download Counter**: Track PDF downloads
   - Field: `downloaded_docs` (already exists, integer: `0`, `1`, `2`, etc.)
   - Increment on each download (contract PDF, invoice PDF)

**Implementation**:
- Frontend JavaScript tracks these events
- On each event, call Vercel API endpoint to queue state update
- Updates batched and applied together (prevents conflicts)
- State used by `payment-router.js` to determine user's current position

**API Endpoints Needed**:
- `api/track-event.js` - Generic event tracking endpoint
  - Accepts: `job_id`, `event_type`, `event_data`
  - Queues update for batch processing

## 3. Test JSON Files with Proper UIDs

**Requirement**: All test JSON files must use proper UID filenames generated by the `uid` command.

**UID Generation**:
```bash
> ~/Development/freelance-payments > uid
Generated UID: uid-rju-024
Mathematical operations: r(56079)=153144 → j(153144)=21 → u(21)=24
```

  - Price 1: `uid-xxx-xxx-1`
  - Price 2: `uid-xxx-xxx-2`
  - Customer: `uid-xxx-xxx-client`
  - Coupon: `uid-xxx-xxx-coupon`

**Test File Structure**:

**Notes**:
