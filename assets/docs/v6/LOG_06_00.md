## Root Cause Analysis

### The BFCache + `unloadHandled` Flag Problem

The issue is a combination of iOS Safari's behavior with PDF links and the `unloadHandled` flag in the event flushing logic.

**Current Code** (`src/App.tsx`, lines 206-219):

```javascript
let unloadHandled = false;
const handleUnload = () => {
  if (unloadHandled) return;  // ← THIS CAUSES THE BUG
  if (eventBufferRef.current.length === 0) return;

  unloadHandled = true;
  const jobId = window.location.pathname.substring(1);
  if (jobId && jobId !== '/') {
    const eventsToSend = [...eventBufferRef.current];
    eventBufferRef.current = [];
    sendEvents(eventsToSend, true).catch(() => {});
  }
};

window.addEventListener('pagehide', handleUnload);
window.addEventListener('beforeunload', handleUnload);
```

**What Happens on iOS Safari:**

1. User clicks "Download" for contract PDF
2. iOS Safari opens the PDF in a **new tab** (ignores `download` attribute for PDFs)
3. **iOS Safari fires `pagehide` on the original page** when focus moves to new tab (aggressive memory management)
4. `handleUnload()` runs:
   - `unloadHandled = true`
   - Buffer `[logged_in]` is sent via sendBeacon
   - Buffer is cleared
5. User closes PDF tab and returns to original page
6. **Page is restored from BFCache (Back-Forward Cache)** - JavaScript state is preserved, including `unloadHandled = true`
7. User signs contract → `contract_signed` added to buffer (buffer is now `[contract_signed]`)
8. User clicks "Download" for invoice PDF → new tab opens
9. **`pagehide` fires again** → BUT `if (unloadHandled) return;` **EARLY RETURN!**
10. **Events NOT sent**, buffer still `[contract_signed]`
11. User acknowledges invoice → `invoice` added to buffer (now `[contract_signed, invoice]`)
12. User navigates to Stripe checkout → `pagehide` fires
13. **`if (unloadHandled) return;` EARLY RETURN AGAIN!**
14. **Events NOT sent**, buffer `[contract_signed, invoice]` NOT flushed
15. Fresh page load with `?session_id=...` (Stripe return)
16. Buffer is empty (fresh page load)
17. Only `payment_1` is sent

**The Core Bug**: `unloadHandled` is set to `true` after the first `pagehide` and is **never reset**. When the page is restored from BFCache, all JavaScript state is preserved, including this flag. Subsequent `pagehide` events are skipped because of the early return check.

---

## The Fix

### Add `pageshow` Event Listener to Reset `unloadHandled`

The `pageshow` event fires when a page is displayed, including when restored from BFCache. The `event.persisted` property is `true` when the page was restored from BFCache.

**Solution**: Add a `pageshow` listener that resets `unloadHandled` when the page is restored:

```javascript
// Add this handler
const handlePageShow = (event: PageTransitionEvent) => {
  if (event.persisted) {
    // Page was restored from BFCache - reset the unload flag
    unloadHandled = false;
  }
};

// Add this listener alongside the existing ones
window.addEventListener('pageshow', handlePageShow);

// Don't forget to remove it in cleanup
return () => {
  // ... existing cleanup ...
  window.removeEventListener('pageshow', handlePageShow);
};
```

**Why This Fixes It**:

1. User downloads PDF → `pagehide` fires → `unloadHandled = true` → buffer sent
2. User returns → `pageshow` fires with `persisted = true` → **`unloadHandled = false`**
3. User continues workflow → more events buffered
4. User downloads again → `pagehide` fires → `unloadHandled` is now `false` → buffer sent correctly
5. ... and so on

## Additional Considerations

### Why Does iOS Safari Fire `pagehide` When Opening New Tabs?

This is related to iOS Safari's aggressive memory management:

1. **Page Lifecycle on iOS**: Safari tries to conserve memory by "freezing" background pages
2. **BFCache**: Pages are stored in the Back-Forward Cache rather than being destroyed
3. **`pagehide` Event**: Fires when a page is "hidden" from view, which includes being backgrounded when another tab takes focus

This behavior is different from desktop browsers where opening a new tab doesn't typically fire `pagehide` on the opener page.

### Why Didn't This Show Up Before?

Previous testing (LOG_06.md) was done in controlled step-by-step scenarios where:
- Users didn't click "Download" for PDFs (or did so on desktop where the `download` attribute works)
- The PDF download path wasn't exercised on mobile
- BFCache restoration didn't occur during testing
